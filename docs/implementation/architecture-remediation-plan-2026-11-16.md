## Assessment against the intended product

The intended product—typed, in-process .NET workflows with explicit ephemeral/durable lifetimes, detached state, predictable resource ownership and replaceable storage—is coherent. The implementation has substantial working machinery and useful certification. The principal weaknesses are integration correctness, silent codec loss, and costs that grow with unrelated or historical work. The earlier remediation plan made these problems more expensive than necessary.

| Area | Assessment | Immediate consequence |
|---|---|---|
| Shared authoring, codec and registration | Typed handles and one compiled plan are good foundations. Fingerprint/profile encodings are ambiguous; supported codec shapes can silently lose values. | Fix identity and value fidelity before expanding the surface. |
| Ephemeral | Detached attempts, structured joins and physical ownership are purposeful. Timeout winner election is incorrect; retention's shared-gate scans need measurement. | Repair deadline arbitration; retain settlement semantics. The start gate is already fixed at this base. |
| Durable engine | Expected-version commits, explicit checkpoints and inbox/outbox boundaries fit the purpose. Envelope/aggregate loading and local-only output observation violate cross-host expectations. | Repair coherent execution loading and distributed observation. Preserve at-least-once delivery semantics. |
| Providers and resource governance | PostgreSQL is the practical primary durable target. SQL Server's ordinary workflow document is a compatibility implementation with global serialization. Full historical governance snapshot replay is avoidable. | Narrow the SQL release promise; recover governance from the latest complete record first. |
| DAG | Authored ordering, isolated mapping and durable child facts are useful. | Evidence, packaging and companions | Many green tests exist, but physical test files are not necessarily compiled, and internal tests do not prove public package journeys. | Each phase must show its executable coverage. Kubernetes qualification remains a separate deliverable. |

## A. Correctness repairs using existing runtime structure

Proposed change: `repair-runtime-correctness`, or the relevant existing owner for unchanged guarantees. Scope is F05, F06, F01 and F03; F04 remains with Task 3.1. Start from the existing failing tests, then add the uncovered concurrency cases. One review covers the phase, with per-finding test evidence; a small repair need not wait for a new program specification.

1. Replace sentinel/delimiter identity encodings. Encode presence and value separately for outcome names; define stable ordering, culture and string encoding for fingerprints. Bump the compiler fingerprint format when semantics change; no legacy alias. Compare normalized typed registration profiles, including every behavior-affecting field. Equivalent registration is idempotent; different profiles fail before service mutation. Legal punctuation remains legal.
2. Make the durable loader own the checkpoint and return that same checkpoint with the rehydrated aggregate. Remove the driver's independent earlier checkpoint read. Read append-only tail from the captured checkpoint version. Never update an expected version while retaining a position that the observed events cannot reconstruct.
3. Establish the missing write invariant: every changed execution envelope must advance the stream's concurrency version through a persisted position-change fact. Baseline `DurableLifecycleCommandHandler.Handle(DurableYieldCommand)` and `Handle(DurableFiberFailedCommand)` can currently emit zero events. Audit all checkpoint writers, including scheduler/attempt admission and reconciliation. Prefer an explicit protocol fact using existing append primitives; do not add an atomic snapshot provider API. This is engine-owned consistency, not a promise that protocol declarations and provider event serialization require no changes.
4. Classify the entire tail. Matching wait/timer completion facts can be reconciled only against their exact blocked obligations; cancellation/park/retry facts must govern whether execution proceeds. Step completion, continue-as-new, registration/consumption, resource ownership and position-change facts require a fresh checkpoint load unless reconstruction is explicitly proven. Terminal facts may stop execution without resuming the prior envelope. Unknown facts fail closed. Bound retries and return retryable contention/no progress while preserving the continuation's retry path; never acknowledge the last wake on a stale read.
5. Keep gap checking conditional. The current `LoadTailAsync` returns events without stored sequence numbers; counting returned events is not gap validation. First determine whether supported retention can remove events needed after a captured checkpoint, including a concurrent newer checkpoint/trimming race. If it can, protect the read or detect that trimming race before executing. Otherwise rely on the existing append-only/expected-version store guarantee for F01 and defer generalized storage-corruption/sequence API hardening; it is not an F01 closure gate across three providers.
6. Use one ephemeral attempt-winner mechanism that compares the runtime clock with the absolute deadline at election. At/after the deadline a new result cannot win. For synchronous handlers sample after invocation returns; for asynchronous handlers sample when the runtime completion callback actually executes. Do not claim access to the producer's unobservable completion timestamp. An already elected pre-deadline result remains the winner even if the consumer runs later. Losing work retains physical capacity until it actually settles; it cannot publish state, outputs or a retry result into a later attempt.

Closure evidence: existing F01/F03/F05/F06 repros green; checkpoint-only position mutation race; start/genesis, publish, continue-as-new and tail-read/append interleavings; safe wait/timer reconciliation; retry exhaustion preserves a wake; exact-deadline and delayed-continuation tests; root/branch/item timeout and retry identity; physical pool/throttle conservation; both-mode fingerprint vectors and registration equivalence/conflict matrix. Add a trimming-race test only if the supported retention audit establishes that risk. Count added position facts, bytes and commits per iteration in a long `While` loop at small/default driver budgets; do not hide the extra per-yield write amplification behind throughput alone. Run focused engine tests and affected PostgreSQL plus retained experimental SQL Server correctness certification. PostgreSQL tests must include the landed facade candidate's checkpoint lineage preservation. Do not require unrelated corruption, package or cluster qualification.

Rejected for A: a new atomic provider read transaction across three providers, a temporary SQL adapter, and dependence on native SQL storage. Atomic reads would not by themselves fix same-version checkpoint replacement. F04 closure must be confirmed on its owner track rather than inferred from this phase.

## B. Shared value fidelity

Proposed change: `enforce-lossless-workflow-values`. **Entry dependency: `admit-dag-public-handle-seam` lands first**, including its DAG run-input round-trip rule. Record its landed commit and build B on it before generalizing or replacing that rule. Do not overwrite the candidate, start a competing contract owner, or establish a second permanent codec policy.

The DAG facade landed in [PR #27](https://github.com/dekrevedko/Workflow-orca/pull/27) at `a822b215`. Budget for a declaration-guard update if Phase B changes any of numbered documents 04, 06, 10, 12, 16 or 17. For example, when adding acceptance criteria to doc 12, verify that removing exactly the Phase B text reproduces the Phase A document before applying the existing Phase A projection. Run the current and historical declaration checks together.

1. Define the supported contract as fidelity of the codec's serialized workflow-value representation, including nullability and declared types. Type-shape admission alone is insufficient. Reject unsupported shapes/values explicitly at the earliest boundary; never silently accept a lossy snapshot. Preserve supported immutable constructor-bound types and source-generated metadata.
2. Inventory every shared codec call site: workflow input, state initialization and detached attempts, committed state/output, events and payloads, DAG run and mapped inputs, child outputs and reopened values. Probe each path before declaring coverage. The three new failing assertions establish only the direct codec, durable input and ephemeral detached state cases.
3. Prototype a small shared validation primitive using the fixed codec and exact declared metadata. The current DAG guard's serialize/decode/re-encode check is the starting point, not an unconditional mandate to serialize every value three times. Combine static rejection of unreconstructable shapes with value-level fidelity checks where needed. Measure allocation/cost, especially ephemeral attempts. Avoid redefining value equality as arbitrary user `Equals`, and do not add user converters/reflection to make an unsupported type appear supported.
4. Decide error ownership at admission and during execution. Registration/start must report the documented unsupported-value outcome before persistence or effects; an invalid replacement produced by running code must fail the owning attempt with useful provenance. Corrupt persisted bytes remain an integrity failure; unsupported local metadata is a different condition. Validate before effects can escape.

Closure evidence: private setter/no constructor, mismatched constructor, writable, init-only, immutable constructor, nested collections, null and polymorphic cases; value mutation and nondeterministic getters; reflection and generated-metadata paths; native AOT package recipe for changed codec paths; cross-mode/public event/DAG boundary coverage. A rejected unsupported value counts as a correct repair when the contract says so. No requirement to preserve all previously accepted CLR shapes.

## C. One bounded observation design for workflows and DAG

Proposed change: `bound-runtime-observation`. **Entry dependency: `admit-dag-public-handle-seam` lands first.** Then amend `developer-facing-surface` / "Completion waits are notification-driven and race-free" and `management-and-querying` / "DAG terminal waiting is notification-driven" after that exact successor. If periodic workflow rechecking is chosen, also amend `management-and-querying` / "Typed committed root state and output are queryable" and `workflow-contracts` / "Workflow success projections and output waits are typed": both independently prohibit polling. Their predecessors are reshape -> settlement, without the facade seam. The current no-polling rules apply until deliberately replaced; an existing DAG recovery poll is not authority to bypass them. Register only each heading's exact successor chain and preserve unrelated ephemeral wait/settlement and DAG fault semantics.

Preferred first correctness option: keep the local wake and add a bounded, cancellation-aware periodic authoritative recheck for durable output waits after amending the no-polling rule. Recheck immediately after subscribing, stop all rechecks on completion/cancellation/shutdown, coalesce local waiters where useful, and define retry/error behavior and a maximum detection interval. Prove remote completion and a lost wake complete within that interval using a controlled clock. Count the resulting read rate. This can close F02 without waiting for the fan-out measurement program below; notifications then improve latency. If polling cost is unacceptable for the supported workload, choose capped durable subscriptions instead. Neither option requires a second permanent observer architecture. Broader observer boundedness remains an explicitly separate finding even if F02 closes first; one review covers the selected phase scope.

1. Measure append latency, lock time and outbox amplification at 1, 10, 100 and 1,000 live subscriptions, plus repeated appends and expired subscriptions. Include DAG progress and workflow completion, slow recipients, reconnect and multiple hosts. Declare the supported subscriber envelope and latency budget before selecting the design.
2. Preferred small design: a finite cap on live provider-side subscriptions per instance/run, atomically enforced across hosts, with renewal/replacement that cannot bypass the cap. Coalesce local callers behind one host subscription where it simplifies the design. Existing subscriptions must remain valid when new admission hits the cap; return an explicit capacity result to new callers. Expiry and cleanup must not scan an unbounded expired population on every commit. Specify bounded cleanup, recipient identities, lease renewal and a recheck after resubscription.
3. Preserve subscribe-before-recheck, durable atomic notification creation, duplicate-safe delivery, recipient-only claims, shutdown/unsubscribe and reconnect behavior. Notifications are wake hints; durable state is authoritative. Bound pending notification growth as well as live subscriptions: repeated DAG appends must not accumulate an unbounded per-recipient backlog. Measure and select bounded coalescing/admission/backpressure with explicit retry semantics.
4. If bounded existing subscriptions cannot meet the declared envelope, design a shared asynchronous expansion/watermark mechanism for BOTH DAG and workflows. Record the measurements and rejected simpler design first. Do not leave an unbounded DAG commit loop alongside a bounded workflow design.

F02 correctness closure: the two-runtime repro passes; completion before/during/after local subscription, remote completion, lost wake, caller cancellation, shutdown, retention/deletion and output absence are covered. With periodic rechecking, prove the detection bound, stopped timers, retry/error handling and read-rate accounting; subscription cap/backlog measurements are not prerequisites to that repair. With durable subscriptions, also prove expiry/renewal, recipient restart, duplicate delivery and cap races on real providers. Separately close observer boundedness with repeated-append/backlog bounds, expired-entry cleanup and terminal-commit cost under the selected cap; keep it open if only the recheck repair is delivered. Public API and provider changes are allowed; reuse concepts and helper logic without forcing unrelated event payloads into one giant abstraction.

## E. Recover governance from the latest full-state record

Proposed change: `recover-latest-governance-state`. This deliberately replaces the current complete `1..Version` recovery requirement. Every committed governance record already contains full state; replaying all old full states is unnecessary for current-state recovery.

1. Add/replace the narrow port operation for latest committed full-state recovery. Return state, its sequence/version and the committed head consistently; validate identity, format, record integrity and all current-state invariants. Missing/corrupt latest state fails closed; never silently fall back to older capacity ownership. Keep expected-version append and atomic multi-pool decisions.
2. Implement indexed latest-record reads for PostgreSQL and behavioral parity for in-memory storage. Under D's recommended experimental SQL scope, adapt SQL Server to the new latest-state semantics while explicitly retaining its full-document/history I/O limitation: `SqlServerResourceGovernanceStore` restores all partition histories through its state engine. Returning only the last record from that document does not qualify bounded storage reads. If SQL Server is selected as a supported v1 provider instead, E must explicitly include a narrow indexed governance-head/storage change, with atomic head/history append and its additional cost; a full ordinary-workflow storage rewrite is still unnecessary for this phase. If SQL Server is removed, no adapter work is required.
3. Keep required identity/tombstone information in the current snapshot. Separate audit/history verification from hot recovery; do not silently promise full historical validation after changing this contract. Explicit audit can still traverse retained history. Test restart, FIFO, duplicate operations, resize/confirmation identity, quarantine and release barriers.
4. Measure fixed live state with increasing history and growing retained identities separately. Latest-only read/decoding cost is O(current snapshot size), rather than the sum of all historical snapshot sizes; total recovery also includes current-state validation and lookup costs. It does not make the current snapshot or writes constant-size. Add an indexed identity ledger, compaction or revised retention policy only in a subsequent change justified by remaining cost.

Closure: PostgreSQL performs one indexed latest read independent of historical row count; all retained adapters demonstrate state/version agreement, corruption failure, equivalent outcomes to full replay on valid histories, and resource conservation/crash barriers. Compare bytes read, decoded records, allocation and latency per provider. Report current-snapshot growth separately. For experimental SQL, close only the engine replay/behavioral portion of F08; the history-dependent read/write cost remains open under the SQL storage owner, triggered before promotion to supported status. Do not claim universal bounded recovery or let that deferred promotion block PostgreSQL/engine completion. Rejected default: immediate ledger redesign across all governance operations.

## F. Measure idle scheduling and retention; change only what fails

Proposed change: `reduce-idle-runtime-work` if measurements justify implementation. Record baseline source, configuration, machine, populations, operation counters and distributions; avoid single elapsed-time anecdotes as acceptance criteria.

For DAG, cover idle runs with spare capacity as well as full runs, ready/stuck mapping, host restart and cross-host progress. Count reads per unchanged run per discovery cycle, pages/rows scanned, seen-set size, worker threads, wake latency and fairness. The owner's earlier five reads in twenty seconds is reported evidence; this review verified the code path but has not repeated that measurement. Prefer safe version-cache invalidation and idle worker retirement before a global scheduler rewrite. Preserve isolated evaluation, authored ordering and physical ownership of stuck user code. An unchanged-state cache must be invalidated by local work completion, lease/retry deadlines, definition availability and remote version changes; a periodic correctness fallback is allowed and must be costed.

For retention, measure 1k/10k/100k entries with different active/terminal/pinned populations, gate hold time and ownership release throughput. If scans dominate, maintain an incremental eligible-terminal index. Set the retention age stamp once physical settlement and facade publication are both complete—even if pinned at that moment. Pinning controls eligibility, not age. Unpinning must not reset age; logical terminality alone must not start it. Preserve whole-unit retirement, key reuse, external settlement and shutdown races.

Closure: a declared operating envelope, before/after counters and equivalent correctness outcomes. If the baseline is acceptable, close the optimization proposal with measurements and retain the limitation in current docs; do not manufacture a redesign. No host-global mapper cap is inferred from the per-run authored concurrency limit.
