# Protocol requirements and verification review

## What the existing requirements settle

* **Sequential waits.** EV-043 and AC-109 allow the next occurrence to use the same signal stream after the first event is consumed. EV-011 and AC-107 require rejection of simultaneous active owners, including within one instance. The corrected ephemeral path accepts the event into the blocked fiber on its execution lane before downstream code can activate another wait. Internally the old reservation stays held until the continuation settles. A duplicate event cannot advance a same-key successor during the retained deduplication window. [Event requirements](../../docs/specs/05-requirements-events-waits-timers.md) and [acceptance criteria](../../docs/specs/12-acceptance-criteria.md)
* **Event identity.** EV-010/011/013/020 and AC-107 describe the routing key using event name alone alongside definition and correlation. Canonical OpenSpec requires exact contract name **and version**, as do the ephemeral matching and index implementations. A future source-spec synchronization should spell out the descriptor consistently in these clauses and EV-043's stream example. Authors needing to distinguish successive occurrences encode that distinction in the correlation ID. [Canonical event identity](../../openspec/specs/event-routing-and-waits/spec.md) and [routing index](../../src/OrcaCore.Engine.Ephemeral/Execution/EphemeralRoutingIndex.cs)
* **Ephemeral caller cancellation.** The product requirements establish observable ordering and uniqueness. The corrected implementation chooses a specific boundary. Before event acceptance, cancellation can leave the predecessor available for retry. Once accepted into the continuation, the instance drives the turn and returns a receipt even if the caller cancels. An exception in user code after acceptance can fail the workflow. This decision concerns event ingress through the process-local bridge and is distinct from workflow cancellation. [Current checks](wait-ownership/README.md#current-implementation)
* **Durable matching and driving.** EV-032 couples wait consumption, inbox progression and the resulting transition. DR-034 preserves runnable work across host loss and gives the continuation pump a separate claim and disposition. The durable model and C# cases cover both sides of the match commit and one committed resume. Qualification of individual SQL backends still requires provider tests. [Durable driver requirements](../../docs/specs/16-requirements-durable-driver.md) and [model scope](durable-wait-handoff/README.md)

The subsequent [continuation lease checks](durable-continuation-lease/README.md) reproduced an extra claim on the in-memory, PostgreSQL and SQL Server providers. An expired worker can reopen a dispatched record with a retry mark. Its release after dispatch has no effect. The replacement pump drained the reopened signal with the same committed history.

## Remaining candidates, in priority order

| Priority | Protocol and specific question | How to test a counterexample |
|---|---|---|
| 1 | **Durable event versus timeout across same-key reuse.** After E1 consumes A and B becomes active, can A's already-claimed timeout or E1's redelivery consume or clear B? | Use two WaitIds, two EventIds, and one delayed timer claim. Compare durable history, timer cancellation, inbox state, and which exact occurrence remains active. EV-043 and EV-051 supply the expected outcomes. |
| 2 | **Ephemeral start-key retirement.** Can a caller that pins an old binding race retirement and creation of a replacement under the same key? | Extend the existing start model with two instance generations, retain/pin/release, and one sweep. Compare replay identity and replacement count against the retirement tests. [Canonical retirement requirement](../../openspec/specs/management-and-querying/spec.md#requirement-ephemeral-start-idempotency-expires-with-atomic-retirement) |

Both candidates extend models with known source mappings and observable failure cases.
