# DAG child join across parent cancellation

CP-023 requires an idempotent child join. Under CP-024, a child cancelled independently of the DAG joins as Failed with code `CHILD_CANCELLED`. A cancellation caused by the DAG joins as Cancelled. The order in which the join worker reads the parent can differ from the order that established the child's terminal fact. [Composition requirements](../../../docs/specs/08-requirements-composition.md#cp-023-one-durable-child-instance-per-node-occurrence)

Bound the model to one live run, an admitted child A and an admitted sibling B that keeps the run open. Separate child terminality, the parent's cancellation barrier, the first join append, the outbox acknowledgement, and one expired claim and redelivery. Compare the current coordinator's use of parent state with a reference that can distinguish the winning child cancellation cause. The cause is known from the test schedule. Whether the runtime persists enough evidence to recover it is part of the comparison.

Check both orders. First, A cancels independently and joins while the parent is running. Lose the acknowledgement, request parent cancellation, reclaim the same notice and replay it. Second, A is already terminal when the parent requests cancellation, and its first join arrives after that barrier. Check exact outcome and code, one committed join, preservation of B's admission, and the notice's final disposition. Include DAG-caused cancellation as a positive control and a genuinely changed terminal fact as an integrity control.

Run TLC with the private JRE. Keep the source profile and contract reference results distinguishable. Run executable schedules alongside the in-memory hosting recovery tests using the child handler, a real outbox claim and the pump. Assert the required outcomes and retain any failing traces and test results. SQL provider behavior, host process death, general DAG scheduling, and a production repair are outside this verification increment.

## Production repair and restart qualification

The durable engine appends one winning `WorkflowCancellationRequestedEvent` before finalizing cancellation. Competing requests can help finalize that cancellation. Only the winning request determines its origin. Use the request's existing command ID to identify the issuing operation. The workflow facade and the owning DAG use separate, reproducible UUIDv8 command identities for the same child. The DAG must have a committed cancellation barrier before issuing its command. The child stream already persists the ID, order and lineage across providers and process restarts.

The first join reads that evidence from the bound child's journal. A retry validates the immutable child facts against the saved node, including output bytes. Neither operation can append a second join. For a legacy request whose random v7 ID predates origin tracking, replay accepts either legal saved cancellation outcome. A first join while the parent is still running can establish independent cancellation. A first join after the barrier with unknown legacy origin must surface an integrity fault and retain the admission. Missing or contradictory journal evidence also requires reconciliation.

Check both orderings across a killed worker and a new process using the same PostgreSQL database. Verify the committed outcome, number of joins, sibling admission, outbox identity and attempt. Retain the changed-output integrity case and a genuinely DAG-caused cancellation. Run the source model with separate request, finalization and recovery actions and retain the original coordinator errors as mutation controls.
