# Durable event versus timeout on a reused key

Can a claimed timeout from occurrence A or a broker redelivery of E1 resolve occurrence B after A has consumed E1? EV-043 allows sequential reuse of a signal stream. EV-044, EV-050, EV-051 and DR-AC-020 bind timeout cancellation and the winner to the wait occurrence. The durable inbox retains the identity of an applied direct event.

Model one durable instance, two sequential structural waits on the same contract and correlation, two distinct wait and timer identities, E1 and fresh E2. Split claiming a timer from processing it. Allow A's timer to win before E1, or let E1 commit the match and cancel A's timer together. Publish B only after A's event resume. Deliver the saved timer command and the identical E1 envelope in either order while B waits. Allow E2 or B's own timeout to settle B. The commit is the serialization point. Timer-first failure of this root workflow ends the path to B.

Check occurrence-specific history, a single winner per wait, cancellation of the losing obligation, and preservation of B across stale inputs when no fresh event is pending. Include reachability traces for both stale orders and genuine event and timeout wins, and controls that deliberately retarget an old timer or forget event deduplication. This is a bounded safety check with retained inbox identity. Broker retention, purges, fanout, wall-clock scheduling and eventual delivery are outside its scope.

Distinguish the envelope that wakes ingress from the event that actually wins. Direct duplicate acceptance can retry delivery of the oldest eligible Received record. Include a schedule where E2 has already been accepted and remains pending while B waits. Redelivering E1 may then drive B, but the second match must name E2 and E1 must remain Applied once.

Replay the schedules on the in-memory, PostgreSQL and SQL Server providers with a real registration, provider timer claim, direct ingress and durable command processing. Compare the journal, active projection, timer identity and inbox disposition after each stale operation and after a legitimate winner. Complete the original scheduler claim by its timer ID. Check root timeout failure and distinguish logical timer cancellation from scheduler acknowledgement. Record which fixtures exercise a scheduler and flag any discrepancy between model and implementation.
