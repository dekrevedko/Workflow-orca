# Idle DAG mapper worker retirement

A DAG run that has admitted a child can wait for hours with no mapping work. At `960c0383` the coordinator kept a dedicated thread throughout that wait. The scheduler now offers the thread for reuse when the previous mapping has returned and either no node is ready or all child slots are occupied. On an unchanged recovery-index row, discovery can retire the offered thread. The next mapping and discovery claim that thread atomically.

The lightweight lane keeps its stream version and any prepared mapping. A changed version still triggers a checkpoint read. While a mapper is physically executing, only its run owns the worker, including after cancellation. A run actively attempting its initial admission can keep its worker until it reaches a waiting state. The ordinary discovery cadence determines when eligible threads retire.

## Correctness

The shared provider test runs two schedules. In one, a second scheduler recovers the first scheduler's run. In the other, the scheduler stays alive and its actual root mapper thread exits while the child remains admitted. A workflow-only host joins the child. The test claims and acknowledges the join's ready notice without delivering it. On the next controlled discovery pass, the scheduler observes the new version and admits the dependent exactly once with input `42` on a different thread. Between unchanged passes, the target's checkpoint read count stays constant. [Provider test](../../../../tests/OrcaCore.ProviderCertification/DagDiscoveryCacheCertification.cs)

Independent review reproduced the same-host failure on the base commit. It also forced admission cleanup to outlast a discovery pass and exposed an extra local read in an early test. The final test waits for the completion visit after release of the root's admission turn before opening discovery. The reviewer repeated that schedule successfully. A separate Hosting test holds the only child slot while a second independent root is ready. It verifies physical thread exit before freeing capacity, then verifies successful admission on a different thread. [Hosting tests](../../../../tests/OrcaCore.Hosting.Tests/DagSchedulerTests.cs)

## Cost

On Windows 11, three independent processes per build each held 64 children open. All three baseline hosts retained 64 active mapper threads after ten seconds and all three candidate hosts had zero active or retired mapper threads. Median process working-set growth over the empty host was 35.93 MiB on the baseline and 32.25 MiB on the candidate. Virtual address space growth fell from 232.93 to 31.98 MiB. These measurements describe the whole process.

A 24-node chain took 17.50 / 19.17 ms at p50 / p95 from a child join to dependent admission on the baseline and 17.42 / 19.32 ms with retirement. Uncontended bursts of 48 ready roots each used one mapper thread on both builds. For 24 independent roots with live child pumps, time to last admission had a 15.5% higher median and a lower p95 in the first nine-run sample. A balanced follow-up alternated four fresh processes per build. Across twelve runs per build, the baseline and candidate medians were 5.972 s and 6.119 s. The p95 values were 7.709 s and 6.933 s. All runs used one mapper thread. Admissions queued 266 and 264 times respectively. The range of observed timings leaves the end-to-end throughput difference uncertain. ## Validation

The source checkpoint is `0c3a9498`. Release built with zero warnings and errors. Core, Ephemeral, Durable, Acceptance, Hosting and in-memory provider certification passed 408, 477, 158, 37, 127 and 136 tests respectively. Infrastructure passed all 323 tests, and strict OpenSpec validation passed all 34 items. The final provider selection covered the two lost-wake schedules and a blocked mapper beside a healthy run on PostgreSQL 17 and experimental SQL Server 2022. All three cases passed on each database. An earlier implementation's two SQL Server lost-wake cases passed, but its separate cancellation control surfaced `DAG_STALE_FENCE` during a loaded run. The final control passed. The cause of that earlier fence expiry remains unverified.

The independent reviewer removed the full-capacity condition in a disposable build. The capacity-one Hosting test failed at the worker-exit assertion. The final code passed that test, the same-host and restarted-host schedules, and the slow-mapper cancellation and authored-order controls. The reviewed product change updates the source digest for the DAG hosting package. This qualification adds evidence under the existing progression change and leaves its broader acceptance tasks with their DAG owners.
