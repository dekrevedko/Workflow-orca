# Resource-governance recovery measurements

Phase E changed startup recovery to request one complete governance record. For a 256-record history with a fixed state, all three providers returned one 302-byte payload and the aggregate decoded it once. The baseline returned and decoded all 256 payloads (77,312 bytes). With 128 retained resize IDs, recovery decoded 7,724 bytes of current state from the same number of records. The current state grows with retained identities.

## Reproduction

Baseline `aba8a6f8c29aca3301c490d99a318db06e268ca8` and reviewed implementation `6d7cf078dea9b1fd2df412f33c0a8a3c3a133f30` ran in separate clean checkouts. The same runner used Release, .NET SDK 10.0.403, .NET 10.0.14 and a Windows 11 Pro x64 host with an AMD Ryzen 9 9950X. PostgreSQL used image `postgres:17-alpine` (`sha256:dc17045ccfd343b49600570ea734b9c4991cf1c3f3302e67df51e3b402dd55c4`), and SQL Server used `mcr.microsoft.com/mssql/server:2022-latest` (`sha256:e07b9699a2b749969f19d86563ceeea22bd3a69f7f1db85a8d1ac4bdaf0c6f56`).

The runner seeded one pool and six histories through the provider’s append port using payload shapes generated by the production engine. Fixed histories repeated a valid complete state at successive sequence numbers. At 256 records, the other three populations introduced one new resize identity at each of the last 16, 64 or 128 records. SHA-256 of every population’s concatenated payloads matched across revisions, providers and instrumented runs.

Each table reports 25 sequential samples per cell of the production aggregate’s `InitializeAsync` on a warmed provider. Elapsed time covers the asynchronous call. Managed allocations use process-wide GC counters bracketing it. P50 and P95 use nearest rank. The runner timed recovery separately from container startup, seeding and explicit audit. Other CI work shared the host and Docker daemon, particularly during the candidate run. These observations measure the distribution on this host. See the [runner](../../../../tools/measure-governance/README.md) and [sample data and query plans](recovery-samples.json).

## Aggregate recovery work

A separate build counted actual aggregate deserializations immediately before decoding each envelope. The record and payload-byte counters at that point equaled what the provider returned in each case.

## PostgreSQL query plan

At 256 fixed-size records the baseline query sorted all 256 rows. It touched 15 shared buffers with one partition. The latest query selected a single record through a backward scan of the existing records primary key with a one-row limit. For one partition, the planner read the one-row stream-head table sequentially (one shared-buffer hit) and the record lookup used two shared-buffer hits. With 1,025 partition heads it used the stream-head primary key (three hits) and the record primary key (two hits). All plans came from the provider’s actual SQL with `EXPLAIN (ANALYZE, BUFFERS)` after `ANALYZE`. Shared hits describe warmed database buffers. Index depth, physical disk reads and cold-cache latency may differ elsewhere.

## Experimental SQL Server document transfer

An administrative query collected the size of the full serialized provider document using `DATALENGTH(payload_json)`. SQL-client connection statistics collected protocol bytes sent and received during a separate single recovery of the seeded partition. The revision delta measures how many times that read rewrote the state row. The baseline rewrote the document once. The latest read left its revision unchanged while still transferring and parsing the complete JSON document. It materialized only the selected governance record.

SQL-client statistics provide partial observations of protocol traffic. The driver reported zero bytes in some windows, including the one-record candidate response even though its query selected and returned a nonempty document. These cells are marked unavailable. Raw data retains the original counters. The independent document-size and revision measurements establish read size and absence of a rewrite. Actual network savings cannot be quantified from these statistics.

The document spans the provider’s governance partitions. This fixture used one partition per schema, so it measures history dependence within a partition. Physical database page and transaction-log I/O lie outside the client and column measurements.
